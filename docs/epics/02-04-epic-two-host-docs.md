### Retro

- The story was planned as a rewrite of four README sections and turned out to be a rewrite of none of them, because epic 02-01 story 5 had already done that work and its coverage row was already verified. What was left was the prose the executable checks are blind to, and it was worse than the sections.

**Every command in the README ran, and the document was still wrong about what it is.** `readme-v2.test.js` classifies every fenced block by a rule and executes it, fails on an unmatched block and fails again on a rule that matches nothing — a genuinely strong instrument, green throughout. The Status section meanwhile said the package was ported to a host it had been moved off, listed spec 01's five epics as the whole build-out while a second specification had delivered four more, and explained `ralph`'s dead loop by reference to that same departed host. None of that is a command, so none of it was reachable from the one place the README is checked.

The reading that closes it derives the epic table from `docs/epics/` **in both directions**: every projected epic document must appear in the table, and every filename the table names must exist. A hand-kept list would have reproduced the original defect exactly — it is only ever edited by whoever remembers to, and nobody remembered for four epics. The table also has to distinguish delivered work from work that has not shipped, which is asserted separately, because a table rendering both alike is true of something on every row and leaves the reader to be the one who is wrong.

**The placeholder was the same failure one word wide.** Command blocks said `<package path>`, which was accurate while there was a package and read as though there still were once the install became a clone. It was also defined four sections after its first use, inside *When something else owns the hook* — a section a reader arriving from a guard refusal has no reason to open, which is exactly the reader who meets it in a command they are about to run. Renamed to `<dpm clone>` and defined where it first appears, with the assertion written as a position check rather than a presence check, because "it is defined somewhere" is what was true before.

Two things followed the rename outward. `readme-v2.test.js`'s `PLACEHOLDER` constant, changed in the same task rather than after the suite went red — retro 03's instrument lesson, applied deliberately. And `scripts/skill-body-check.ts`, whose recorded-gap message printed the identical stale claim about the departed host; the README's own sentence had just been rewritten and the script's had not, which is retro 04's question — what else in this tree produces the same artefact for a reader — answering itself one grep later.

**No coverage was marked verified, and that is the story's most considered act.** All three bindings quote FR6's two-host text. The criteria were amended to drop the second host at Chris's ruling; the fragments could not be, because the spec is read and not written. Marking them would have recorded the README as covering a host this story's own must-NOT forbids it from naming. FR6's v1 half is discharged already by two correctly-scoped rows epic 02-01 wrote. The three two-host rows are left standing and unverified rather than retired, so the divergence between the specification and the decision that overtook it stays visible to whoever revises the spec.

### Retro

- **The story's own control found a dead pattern in the story's own must-NOT, on the first run.** The sweep for claims the section had stopped making true was written line-anchored — `/^[^\n]*reads a file from the package directory[^\n]*$/m` — which reads naturally and cannot work, because the README is hard-wrapped and the sentence it was written against breaks between `package` and `directory`. It passed against the current section, where there is nothing to find, and would have gone on passing for the life of the project while a third of the must-NOT constrained nothing. What caught it was the control planting the removed paragraph *verbatim* and asserting all three patterns report, rather than asserting that some did. `tests/support/skills.js` records this trap for skill bodies; it is a property of every hard-wrapped document here, and the fix is `\s+` between every word rather than a space.

That is the retro-07 disposition this run recorded before starting — *run the reading and look at what it returns before asserting an absence over it* — paying for itself inside one story, on a pattern written by the run that had just written the disposition down.

**The defect the story was fixing was one this run caused.** Epic 02-03 removed the `external_directory` rule and left the two paragraphs framing it, so the section opened by telling every reader that one entry was worth setting whatever their configuration looked like, three paragraphs above the text saying nothing DPM does reads outside the project. Nothing noticed: the checks over this section ask whether documented *rules* name skills and tools that exist, and prose is not a rule. The section had been internally contradictory for an epic and every test was green.

**The reading the criterion actually needed was the other half of a partition.** `permission-entries.test.js` already asked whether each recommended rule finds a skill. It never asked whether each skill finds a rule — and a recommendation that names only real skills can still leave half the method denied, invisibly, because the rule matches *something* and the first test passes. Story 2 adds skills → rules, and the two together are the partition retro 06 named after four green files that each checked one side of one.

Two things kept it honest. It reads `discoverSkills`, because what the permission engine matches is the string the host is handed, not the directory listing — and before ADR 02-04 those differed, which is precisely the state in which `dpm-*` matches every registration and nothing a reader can find in the tree. And the README's claim about where the id comes from is checked *against the tree* rather than only found in the prose, so the sentence cannot outlive the mechanism the way the paragraph above it did.

**No fourth transcribed list.** The criterion wanted the twenty-three held against the published ids, and `corpus.test.js` already transcribes them with `suite-skill-names.test.js` policing the region. A copy here would have been a fourth thing to keep in step rather than a second opinion, so what is asserted locally is the count — enough to fail when a skill goes missing, and no more than this file has a right to claim.

**One of the two coverage rows was left unverified deliberately.** Its fragment quotes FR7's premise that the engine matches "the unprefixed front-matter name". Epic 02-02 put the prefix into the front matter and dissolved that premise, so the README now correctly says the opposite of the text the row binds. FR7 is another requirement written to fence a risk that no longer exists.
