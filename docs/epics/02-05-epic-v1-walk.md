### Task 3 — Write tests for Host-independent artefacts, without models

**Status**: complete  

Covers the two `unit` criteria and the `integration` cross-server comparison, with the planted host identifier as the sweep's control.

### Retro

- The criterion said "written through the v1 server ... read through the v2 server", and the first thing the story had to establish is that **there is no such pair of servers**. `localServer()` computes one command and hands the same one to whichever host asks, so a test looking for a difference in what dpm *registers* finds none and reports agreement it never earned. What actually differs is the process that ends up running the file, and `src/plugin/server.ts` already had it written down: v1 must use `node`, because the bun compiled into 1.18.25 is 1.3.14 and has no `node:sqlite`; v2 can use its own bun, 1.4.0, which does. Both were re-read off the machine rather than taken from the comment — `BUN_BE_BUN=1 opencode2 -e` printed `1.4.0` and a `DatabaseSync` function — and the comparison became two runtimes over one database. Byte-identical dump, byte-identical projection, guard exit 0 on both.

**Three things were built as controls and one of them caught something.** The planted-identifier sweep asserts the exact set of six `why` values comes back from the dump and from the projection independently, per retro 09; a stale-dump control holds `publishThrough`'s removal in place, without which a runtime that did nothing would hand back its predecessor's bytes and every comparison would pass on the strength of the failure; and the divergence control was rewritten mid-story to run the *same* `distinct()` the real assertion uses, because a control that builds its own equality proves that equality works rather than that the comparison can see. The one that caught something was in `suite-integrity.test.js`: the new stand-down check reported *itself*, because its planted literals sit in the file and `withoutComments` strips comments but not strings. The fix was a line anchor — legitimate here, where the subject is source and a stand-down is a statement, and the opposite of retro 09's trap, which was anchoring against hard-wrapped prose. It is recorded in the comment as having arrived by failing rather than by being remembered.

**Two findings the story did not go looking for.**

First, `docs/epics/02-05-epic-v1-walk.md` renders "Story 2 — Blocked by: Story 3" while the row says `source=story 2, target=story 3, kind=blocks`, and `readiness.ts:15` states the contract in as many words: *"An edge reads source-blocks-target, so the epic that cannot start is the target."* `src/projection/load.ts:112` loads a story's edges by `source_story_id` — the edges where the story **is** the blocker — and `src/projection/templates/epic.ts:101` renders their targets under `**Blocked by**`. Wrong end and wrong label. The readiness query and `list_story ready:true` are correct; only the document is wrong, which is the shape `epic.ts`'s own docblock warns about — *"Neither is wrong on its own terms, both report success, and the reader believes the file."* Out of this epic's scope and left unfixed rather than absorbed.

Second, ENVX1's real reading is not the one the criterion's words produce. Running the suite with both binaries off `PATH` gave 1185/1185 and zero skipped — and proved nothing, because `installed-runtime.test.js:46` and `v1-integration.test.js:46` reach the v1 CLI by absolute path under `$HOME/.opencode/bin`. With a `HOME` holding no `.opencode` the numbers are 1183 pass, 0 fail, 2 skipped. The two skips turned out to be the good kind — each names ENVX1 as its warrant, states what the skip costs, and leaves a companion control that runs on any machine — so the silent binary dependency task 2 went looking for is genuinely absent. What was absent instead was any record that there are exactly two: the existing must-NOT is anchored on `test.skip(` and `{ skip: true }`, and cannot see the runtime `t.skip()` form both of these use. That gap is now closed by a named exact set in both directions.

## Story 2 — Install under a real v1 host

**Status**: complete — All four live criteria met against OpenCode 1.18.25 from a throwaway project outside the checkout; C2 was superseded at the epic's change moment. Getting there required changing the install surface: epic 02-01's recorded "Two entries, embedded skills" was falsified by the host, and Chris ruled at a second change moment to adopt `plugin` + `skills` instead. src/plugin/skills-entry.ts and src/plugin/skill-registry.ts deleted, package.json's ./skills export dropped, README install section rewritten, tests/v1-skills.test.js replaced by tests/skills-registered.test.js, and nine other test files re-aimed.  
**Blocked by**: Story 3  

### Acceptance Criteria

- `opencode --version` reports a 1.x build matching the version the v1 types are taken from, so the CLI and the types the registrar is checked against are the same release. `[manual]`
- `opencode2 --version` reports a `0.0.0-beta-*` build matching the v2 SDK. `[manual]`
- The plugin installed into a throwaway project outside this checkout, under the 1.x host, has its MCP server reach connected state with the skills advertised. Amended from "under each host" at epic 02-05's change moment: epic 02-01 dropped the second host by decision and epic 02-04's README must-NOT forbids naming it, so an install verified under a host DPM refuses to document would be verifying a promise nobody made. The throwaway project is what distinguishes this from the registries criterion below — it is the README's install path walked from cold, in a directory that is not the one the port is developed in. `[manual]`
- A v1 session completes a turn against the contributor's model provider. `[manual]`
- The plugin loads under a 1.x host and its MCP server and skills appear in that host's registries. `[target]`

### Task 1 — Verify both CLI versions against the SDKs they are typed to

**Status**: complete — Scope narrowed from "for each host" to the one host, following the change moment that superseded C2 — epic 02-01 dropped the second host by decision. Verified: `opencode --version` reports 1.18.25, and node_modules/@opencode-ai/plugin-v1 resolves to @opencode-ai/plugin@1.18.25 — read from the installed tree rather than the manifest alone. Beyond the version match, the SDK types and the running host were found to DISAGREE: the SDK's v2/promise Plugin is `{id, setup}` and 1.18.25's loader for the `plugin` config key requires a function export or a default `{id, server()}`. The route that does accept `{id, setup}` is fed by a `plugins` config key the host strips as "cannot be represented in V1". So a version match is not a compatibility check, which is the finding this task turned up.  

Confirms the CLI and the types the registrar is checked against are the same release, for each host.

### Task 2 — Install into a throwaway project under each host and observe the server connect

**Status**: complete — Scope narrowed to the one host, as task 1. Done in a throwaway project outside the checkout with a fresh XDG_CACHE_HOME per run (v1 caches plugin loading per project; a stale entry silently skips a route). The observation the task asked for took four rounds because the first three found defects rather than a connection: (1) neither entry loaded — index.ts had a non-function export and 1.18.25 refuses a module on the first export that is not a plugin; (2) with that fixed, skills-entry.ts still failed, and reading the loader out of the CLI binary showed why — its route is fed by a `plugins` config key the host strips; (3) with the skills moved to the `skills` config key, the server registered but reported `server unavailable key=dpm status=failed`, because RUNTIME is the bare string `node` resolved off the HOST's PATH, where node was 22.18.0 and dpm's own version guard refused. FINAL READING, node 24 on PATH, `opencode serve` against the current tree: 0 ERROR lines, 0 compatibility diagnostics, /mcp = {"dpm":{"status":"connected"}}, `node .../bin/dpm-mcp.ts` running as a child process, /skill = 54 skills of which 23 are dpm-*. Control: the same host without the `skills` key reported 31 skills, 0 of them dpm's.  

Scratch projects outside the checkout, deleted after. Reaching connected state with the skills advertised is the observation; the walk itself is story 3.

### Retro

- Four green suites in a row certified an install that had never once loaded. The story's job was to watch the plugin come up under a real 1.18.25 host, and what it found instead was three stacked defects, each hidden by the one above it. (1) `index.ts` exported a constant beside its route, and 1.18.25 walks every export of a plugin module and refuses the whole module on the first one that is not a plugin — one ERROR line, then a session with no server. (2) With that fixed, `skills-entry.ts` still would not load, and the reason was not in its shape at all: its route is fed by a `plugins` config key that v1's configuration layer strips before any loader sees it, logging `path=["plugins"] kind=unsupported action="Omitted native setting that cannot be represented in V1"`. There is no arrangement of exports by which a plugin registers a skill on this host — the v1 SDK's `Hooks` has no skill member — so the second entry had nowhere to run and was deleted. (3) With the skills moved to the `skills` config key, the server registered and then reported `server unavailable key=dpm status=failed`, because `RUNTIME` is the bare string `node` resolved off the HOST's PATH rather than the developer's, and the node there was 22.18.0 — dpm's own version guard refusing, correctly, into a log nobody reads.

The through-line is that every one of the 1185 tests reached into a module and called its export itself. `tests/support/host-contexts.js` says of itself "this is a recording and not a model", and that was true of the context SHAPE it recorded and false of the module ACCEPTANCE RULE it never probed. A driver that calls `entry.server(...)` is asking a question about the module, and that question can only ever be answered yes. Library lesson 05 — ask the host, not a test's idea of the host — named this exactly, and the suite still had no test that could fail.

What broke the deadlock was reading the loader out of the compiled CLI binary rather than reasoning from the SDK types, which turned out to disagree with the host: the SDK publishes `Plugin = {id, setup}` for a route the host it ships with cannot reach. Once the loader was legible the fix was obvious and the probes became cheap. `opencode serve` was the instrument that mattered — it stays up, and `/config`, `/mcp` and `/skill` answer directly, so "the server reached connected state" and "23 skills are registered" stopped being inferences from the absence of an error line and became readings. The absence of an error line is exactly what a run that never reached the loader produces, which is why the earlier rounds were unreadable.

Two consequences were accepted rather than absorbed. ADR 01-08's profile seam loses its skills half — a directory the host walks takes no options — which changes nothing today because `full` is the only profile there has ever been, but FR13's `lite` will need another mechanism. And the clash alarm is gone: `displacedSkills` read the registry back and named any `dpm-*` entry that was not dpm's own, and there is nowhere to run it now. Probing what replaced it found something worse than expected — two entries in one `skills` array both declaring `dpm-probe` resolved last-one-wins with NO warning logged at all. The host's `duplicate skill name` warning fires between discovery roots, not within the array. So ADR 01-05's prefix is now the entire defence, the README carries the ordering hazard for the user, and `readme-host.test.js` pins that it does.

## Story 3 — The end-to-end walk

**Status**: complete — All four criteria met against a running 1.18.25, as one continuous trip. The walk found one defect the four green story-2 stories could not: the README's Permissions section was written in OpenCode 2's `permissions` array, which v1 refuses the whole configuration over, so a reader who pasted the recommended block got a host that would not start. Rewritten onto v1's singular `permission` object, verified live in both directions, and the reading that missed it repaired — `permission-entries.test.js` parsed `.permissions ?? []`, which over the wrong shape is an empty list every loop passes over.  
**Blocked by**: —  

### Acceptance Criteria

- A v1 session starts a dpm skill by the documented invocation, the skill obtains its conventions, a dpm tool writes a row, and `dpm-guard` accepts the resulting commit. The evidence is the row, the regenerated projection and the commit. `[manual]`
- In a real v1 session, a dpm skill starts and performs a step that only the conventions prescribe — a session row created with `skill` and `phase` set, per the shared Session Startup procedure — observable in the database rather than inferred from the transcript. `[manual]`
- Following the README's v1 instructions verbatim produces a working install, a guard symlink that resolves, and a refusal on a deliberately stale projection. `[manual]`
- Under a running v1 host, a `deny` rule written as the README recommends blocks a dpm skill, and the same session without the rule runs it. The two directions are each other's control: a block that would have happened anyway proves nothing. `[manual]`

### Task 1 — Drive the v1 walk end to end and record the evidence

**Status**: complete — Driven end to end against 1.18.25 in a throwaway project outside this checkout. A real session invoked `dpm-quick` through the skill tool, called `dpm_read_shared_document` for the conventions, wrote a session row, a quick document, three criteria and an observation, closed the quick, and the guard accepted the commit that carried the projection and `.dpm/dpm.sql`. Evidence: session row `dpm:quick`/`complete`, `docs/quick/01-quick-deploy-verbose-flag.md`, commit 7d2a28a with `.dpm/dpm.db` correctly excluded by the `.dpm/.gitignore` the first tool call wrote. The commit was first attempted with nothing published, as the control: the guard refused and named both missing artefacts and the absolute publish command.  

One session covering invocation, conventions, a written row and an accepted commit. The evidence is the row, the regenerated projection and the commit — not the transcript.

### Task 2 — Walk the README's v1 instructions and the stale-projection refusal

**Status**: complete — Followed verbatim, and the install and hook halves held: the two config keys produced a session with the MCP server connected and 23 `dpm-*` skills, `ln -s <clone>/hooks/pre-commit .git/hooks/pre-commit` resolved, `git config core.hooksPath` printed nothing, and a hand-edited line in the generated document was refused by name with the edit left in place. The Permissions half did not: it was written in OpenCode 2's `permissions` array, which 1.18.25 refuses the whole configuration over — `Error: Configuration is invalid ... V2 permissions are not supported by OpenCode V1`. Rewritten onto v1's singular `permission` object and re-verified live.  

Followed verbatim rather than adapted — the point is whether the written instructions work, not whether the installer knows what they meant.

### Task 3 — Exercise the permission deny rule in both directions

**Status**: complete — Both directions, same prompt, same project, one line of config apart. With `"permission": { "skill": { "dpm-*": "deny" } }` the skill tool refused and printed the ruleset that stopped it; with the entry removed the identical call returned the body of `dpm-templates`. Two further readings taken while establishing the shape: a tool key is accepted where the host's own key list has no entry for it, and denying one removes the tool from the model's set entirely rather than refusing at call time — `"dpm_*": "deny"` yields a session that reports having no dpm tools at all. The README's recommended allow-list was then run as written: skill body loaded, 184 dpm tools present, `dpm_publish: "ask"` accepted alongside `dpm_*: "allow"`.  

With the rule and without it. The second run is the control: a block that would have happened anyway proves nothing.

### Retro

- **`?? []` is how a test reads the wrong document and reports nothing.** The README's Permissions section had recommended OpenCode 2's `permissions` array — an array of `{ action, resource, effect }` — through four stories of a README the project had already retargeted at v1 alone. v1 does not ignore that key: it reports `Configuration is invalid` and the session does not start, so every reader who pasted the recommended block got a host that would not come up.

Ten tests in `permission-entries.test.js` were pointed at exactly this. They read the section's fenced JSON with `JSON.parse(block).permissions ?? []` and got an empty list, which every loop in the file passes over in silence — "every documented rule is well-formed" is trivially true of no rules, "every skill is covered by a recommended rule" was the one that should have failed and did not, because `allowed.length > 0` was the only floor and it was checked against a list built from the same absent key. `readme-v2.test.js` checked the same blocks for parsing to a non-empty object, which the wrong shape does. Four green files, a rule with a provenance comment, and a recommendation that could not load.

The floor idiom this project uses everywhere — assert the corpus is non-empty before filtering it — was present and did not help, because it was applied to the *result* of the wrong reading rather than to the reading itself. `rules.length >= 3` says the extractor found three things; it says nothing about whether the three are the three in the document. What catches this is asserting the **shape you refuse** as an absence, not the shape you accept as a presence: `refusedBlocks()` must be empty, driven red over a planted block first.

The general form: a reader with a default is a reader that cannot report failing to find its subject. Every `?? []`, `?? {}` and `?? ''` in a test that reads a document is a place where a renamed key becomes a clean pass.

**And the walk is what found it, which is the second half.** No amount of reading the README against itself would have surfaced this — the section is internally coherent and describes a real permission model, just a different host's. It took pasting the block into a project and starting `opencode`. Story 2 established that the suite could not see whether the host would accept dpm's modules; story 3 establishes the same about whether the host will accept dpm's documentation. Both were answered by one command, in a throwaway directory, in under a minute.

## Retro Applied

- 06 · Codebase Discoveries · applied — Retro 06: "poll for the marker, and treat its absence as a reading rather than as a timeout." This is the operating technique for every live-host invocation in the epic. `opencode run` is non-interactive, so each probe writes to a log, is polled for a specific marker, and is killed on it; a probe that stops early or never prints its marker is recorded as evidence about the host rather than retried as a slow fixture. The daemon side has the same shape — MTPLX on 127.0.0.1:8000 was confirmed serving by reading /v1/models, not by assuming the launch succeeded, and its stdout is the log that says whether a turn actually reached the model.
- 07 · Codebase Discoveries · applied — Retro 07: "a predicate does not have to stop matching to go quiet, it can have been quiet from the day it was written. The tell is that a check for an absence has never once reported anything." Story 1 C1 is a must-shaped criterion with a must-NOT interior — nothing in the dump or the projection records which host wrote it — and it already names its control in its own text. This run treats that as binding rather than decorative: the planted host identifier goes into a real row in a real database, the sweep is run and seen to report it by path and by row, and only then is the sweep run over the clean artefact. A sweep whose first ever execution returns empty has not been verified.
- 06 · Complexity Underestimates · applied — Retro 06: "a documented procedure with executable guards has a blast radius the guards make visible only when you change it", plus its recorded residue — with a checkout install there is no released DPM standing apart from the working tree, so a bug in the guard now blocks committing its own fix. Story 3 C3 walks the README's instructions verbatim into a working install and expects a refusal on a stale projection, which means it exercises exactly that regression. Two consequences for this run: the throwaway project is deliberately outside this checkout so the walk cannot be rescued by the development tree, and the guard exercised in the walk is the one the README names rather than the installed plugin used for this repo's own commits. Where the walk trips the known regression, that is recorded as a finding of the walk rather than worked around.
- 07 · Criteria Gaps · applied — Retro 07: "when a criterion's measure can move without the subject moving, it is measuring something else. Ask what else can move it before writing the number down." Story 1 C3 asks that the full suite passes on a machine with neither host binary on PATH. Two things can move that measure without the suite moving: a PATH stripped so aggressively that node itself is unreachable, which fails for the wrong reason, and a test that skips silently when a binary is absent, which passes for the wrong reason. So the reading is not a bare exit code — it records the pass count against the committed baseline and asserts zero skipped, and it establishes positively that a `which` for both binaries returns nothing inside the same shell that runs the suite.
- 08 · Criteria Gaps · applied — Retro 08: "Three green stories left the epic's actual claim unchecked, and only a story written to walk the whole trip found it. The gap sat exactly at the seams, where each story's assertions stopped." This epic IS that walk, one specification up — nine epics have each proved their own piece and none has started a skill in a real session and followed it to a commit the guard accepts. So the disposition is structural rather than a technique: story 3 is not permitted to be decomposed into per-seam checks that each pass. It runs one continuous trip and the evidence is the trip. The retro's second half applies directly too: extract the argument from the artefact rather than writing it down. The skill the walk starts, the conventions it obtains and the tool it calls are read out of the registered bodies and the running host's registries, not typed from memory — and the control matters more than usual, because "the walk succeeded" is also what a walk that extracted nothing and started nothing produces.
- 08 · Patterns Worth Reusing · not_applicable — Retro 08's "a parity oracle is a floor, and an equality says it is a ceiling" — the INHERITED/ADDED reshape, with the note that the two remaining equality assertions, parity-v070.test.js's dump and the corpus snapshot, should be reshaped when they hit their expiry. Set aside because this epic adds no tool, no skill and no test-corpus member: it verifies what is already built against a live host. Neither remaining equality is touched, so neither reaches its expiry here. Recorded rather than skipped silently because story 1 C2 does compare two dumps for byte-identity, which reads like the same shape and is not — that comparison is between two readings of one database, where equality is the property itself rather than a stand-in for a floor.
- 09 · Patterns Worth Reusing · applied — Retro 09: "a control that asserts a non-empty result is weaker than one that asserts the exact set, because the first is satisfied by the patterns that already worked" — and its uncomfortable half, that knowing the lesson did not apply it, for the second epic running. Story 1 C1's sweep will carry several patterns (a host binary name, a version string, a config path, a provider id). The control plants an artefact carrying every one of them and asserts the exact set of hits, not that hits occurred. Written down here because the last two epics both dispositioned this lesson and then failed it inside the same run; the specific trap last time was a line-anchored pattern against hard-wrapped text, so no pattern in this epic's sweeps is line-anchored unless the thing it matches genuinely cannot wrap.
- 06 · Testing Gaps · applied — Retro 06: "a negative reading needs a positive control listed alongside it in the same run, because the failure being guarded against is the run not reaching the code". This epic is almost entirely negative-prone readings of a live host — an MCP server that did not connect, a skill that did not appear, a deny rule that blocked nothing because the session never started. Every host probe in stories 2 and 3 carries a known-good entry beside the entry under test, answered by one invocation. Concretely: the deny-rule criterion (story 3 C4) runs the same skill twice in one harness, with and without the rule, and the run that is supposed to succeed is the control for the run that is supposed to be blocked. A blocked-looking result with no companion success is a reading of the harness, not of the permission engine.
- 06 · Testing Gaps · applied — Retro 06: "when a module hands a value to something outside the process, at least one check must exercise the outside" — four green files had asserted the registration equalled the thing that built it, which is true of a command that cannot start. That finding is this epic's whole warrant, and it is the reason the epic exists rather than being folded into 02-01. Nothing in stories 2 and 3 may be satisfied by a reading of the port's own source or of a test double: each is answered by a real 1.18.25 host process, and the evidence recorded is what that process printed. Corollary carried too — agreement among readings of one source is not evidence, so a criterion satisfied by two of our own tests agreeing is not satisfied.
- 09 · Testing Gaps · applied — Retro 09: "an executable check over a document tests the half of it nobody misreads … derive the list from the tree in both directions." Story 3 C3 takes the README's install instructions verbatim into a fresh directory. The lesson's bearing here is that the fenced blocks already have an oracle in readme-v2.test.js and it stays green regardless, so the walk's value is in the parts between the blocks — the order the steps are in, the assumption that a step's output is what the next step needs, the `<dpm clone>` substitution a reader has to perform. The walk records where a reader following the document in order would stop, and any gap found becomes README text plus a check derived from the tree rather than a hand-kept note.
