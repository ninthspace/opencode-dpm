# The v1 walk — what the suite could not see

**Number**: 10  
**Source epic**: 02-05  
**Status**: complete  

## Observations

- Codebase discovery · Testing gap — The criterion said "written through the v1 server ... read through the v2 server", and the first thing the story had to establish is that **there is no such pair of servers**. `localServer()` computes one command and hands the same one to whichever host asks, so a test looking for a difference in what dpm *registers* finds none and reports agreement it never earned. What actually differs is the process that ends up running the file, and `src/plugin/server.ts` already had it written down: v1 must use `node`, because the bun compiled into 1.18.25 is 1.3.14 and has no `node:sqlite`; v2 can use its own bun, 1.4.0, which does. Both were re-read off the machine rather than taken from the comment — `BUN_BE_BUN=1 opencode2 -e` printed `1.4.0` and a `DatabaseSync` function — and the comparison became two runtimes over one database. Byte-identical dump, byte-identical projection, guard exit 0 on both.

**Three things were built as controls and one of them caught something.** The planted-identifier sweep asserts the exact set of six `why` values comes back from the dump and from the projection independently, per retro 09; a stale-dump control holds `publishThrough`'s removal in place, without which a runtime that did nothing would hand back its predecessor's bytes and every comparison would pass on the strength of the failure; and the divergence control was rewritten mid-story to run the *same* `distinct()` the real assertion uses, because a control that builds its own equality proves that equality works rather than that the comparison can see. The one that caught something was in `suite-integrity.test.js`: the new stand-down check reported *itself*, because its planted literals sit in the file and `withoutComments` strips comments but not strings. The fix was a line anchor — legitimate here, where the subject is source and a stand-down is a statement, and the opposite of retro 09's trap, which was anchoring against hard-wrapped prose. It is recorded in the comment as having arrived by failing rather than by being remembered.

**Two findings the story did not go looking for.**

First, `docs/epics/02-05-epic-v1-walk.md` renders "Story 2 — Blocked by: Story 3" while the row says `source=story 2, target=story 3, kind=blocks`, and `readiness.ts:15` states the contract in as many words: *"An edge reads source-blocks-target, so the epic that cannot start is the target."* `src/projection/load.ts:112` loads a story's edges by `source_story_id` — the edges where the story **is** the blocker — and `src/projection/templates/epic.ts:101` renders their targets under `**Blocked by**`. Wrong end and wrong label. The readiness query and `list_story ready:true` are correct; only the document is wrong, which is the shape `epic.ts`'s own docblock warns about — *"Neither is wrong on its own terms, both report success, and the reader believes the file."* Out of this epic's scope and left unfixed rather than absorbed.

Second, ENVX1's real reading is not the one the criterion's words produce. Running the suite with both binaries off `PATH` gave 1185/1185 and zero skipped — and proved nothing, because `installed-runtime.test.js:46` and `v1-integration.test.js:46` reach the v1 CLI by absolute path under `$HOME/.opencode/bin`. With a `HOME` holding no `.opencode` the numbers are 1183 pass, 0 fail, 2 skipped. The two skips turned out to be the good kind — each names ENVX1 as its warrant, states what the skip costs, and leaves a companion control that runs on any machine — so the silent binary dependency task 2 went looking for is genuinely absent. What was absent instead was any record that there are exactly two: the existing must-NOT is anchored on `test.skip(` and `{ skip: true }`, and cannot see the runtime `t.skip()` form both of these use. That gap is now closed by a named exact set in both directions.

**The criterion's words named a comparison that did not exist, and finding the real one was the story.** "Written through the v1 server, read through the v2 server" presupposes two servers; `localServer()` builds one command for both hosts, so the difference is not in what dpm registers but in which runtime ends up executing the file. The story found the real axis — two runtimes over one database — by re-reading both off the machine rather than trusting the comment that recorded them.

That is the epic's pattern in its mildest form: **a written artefact describing a mechanism that has moved.** Here it was a criterion, and the cost was an hour of reorientation. In story 2 it was the SDK's own types, and the cost was three stacked defects behind 1185 green tests. In story 3 it was the README's Permissions section, and the cost was a documented install that could not start a host. Same failure, three degrees of severity, and in every case the only thing that surfaced it was going and looking at the running thing.

The two findings the story did not go looking for are also the epic's pattern. The projection's "Blocked by" inversion is a document that is wrong while every query behind it is right — `epic.ts`'s own docblock names that shape. ENVX1's reading was 1185/1185 with both binaries off `PATH`, which proved nothing, because two tests reach the CLI by absolute path; the honest reading needed a `HOME` with no `.opencode` in it. **A check that passes because it did not reach its subject is indistinguishable from one that passed.** That sentence is the whole retro.

- Codebase discovery · Scope surprise · Testing gap — Four green suites in a row certified an install that had never once loaded. The story's job was to watch the plugin come up under a real 1.18.25 host, and what it found instead was three stacked defects, each hidden by the one above it. (1) `index.ts` exported a constant beside its route, and 1.18.25 walks every export of a plugin module and refuses the whole module on the first one that is not a plugin — one ERROR line, then a session with no server. (2) With that fixed, `skills-entry.ts` still would not load, and the reason was not in its shape at all: its route is fed by a `plugins` config key that v1's configuration layer strips before any loader sees it, logging `path=["plugins"] kind=unsupported action="Omitted native setting that cannot be represented in V1"`. There is no arrangement of exports by which a plugin registers a skill on this host — the v1 SDK's `Hooks` has no skill member — so the second entry had nowhere to run and was deleted. (3) With the skills moved to the `skills` config key, the server registered and then reported `server unavailable key=dpm status=failed`, because `RUNTIME` is the bare string `node` resolved off the HOST's PATH rather than the developer's, and the node there was 22.18.0 — dpm's own version guard refusing, correctly, into a log nobody reads.

The through-line is that every one of the 1185 tests reached into a module and called its export itself. `tests/support/host-contexts.js` says of itself "this is a recording and not a model", and that was true of the context SHAPE it recorded and false of the module ACCEPTANCE RULE it never probed. A driver that calls `entry.server(...)` is asking a question about the module, and that question can only ever be answered yes. Library lesson 05 — ask the host, not a test's idea of the host — named this exactly, and the suite still had no test that could fail.

What broke the deadlock was reading the loader out of the compiled CLI binary rather than reasoning from the SDK types, which turned out to disagree with the host: the SDK publishes `Plugin = {id, setup}` for a route the host it ships with cannot reach. Once the loader was legible the fix was obvious and the probes became cheap. `opencode serve` was the instrument that mattered — it stays up, and `/config`, `/mcp` and `/skill` answer directly, so "the server reached connected state" and "23 skills are registered" stopped being inferences from the absence of an error line and became readings. The absence of an error line is exactly what a run that never reached the loader produces, which is why the earlier rounds were unreadable.

Two consequences were accepted rather than absorbed. ADR 01-08's profile seam loses its skills half — a directory the host walks takes no options — which changes nothing today because `full` is the only profile there has ever been, but FR13's `lite` will need another mechanism. And the clash alarm is gone: `displacedSkills` read the registry back and named any `dpm-*` entry that was not dpm's own, and there is nowhere to run it now. Probing what replaced it found something worse than expected — two entries in one `skills` array both declaring `dpm-probe` resolved last-one-wins with NO warning logged at all. The host's `duplicate skill name` warning fires between discovery roots, not within the array. So ADR 01-05's prefix is now the entire defence, the README carries the ordering hazard for the user, and `readme-host.test.js` pins that it does.

**The suite could not fail, and nothing about it looked wrong.** Every driver reached into a module and called its export itself — a question about the module, answerable only yes. `host-contexts.js` had written "this is a recording and not a model" about itself, and that sentence was true of the context *shape* it recorded and false of the module *acceptance rule* it never probed. Library lesson 05 already said *ask the host, not a test's idea of the host*; the lesson was in the library, applied at the retro gate, and the suite still had no test that could go red.

That is the sharpest thing in this epic. **A lesson can be correctly recorded, correctly recalled, and correctly dispositioned, and still not be applied — because applying it means building a fixture that starts a host, and every incremental step points the other way.** Nothing was lazy here. Each of the four green suites was a reasonable next thing to write. The gap was structural: no test in 1185 could observe the boundary, and no test that could observe the boundary was cheap enough to be the obvious next one.

What broke it was **finding the oracle** (library lesson 03) in an unexpected place: the compiled CLI binary, read with `strings`, in preference to the SDK types — which turned out to publish a route the host it ships with cannot reach. Once the loader was legible the probes became cheap, and `opencode serve` turned three inferences into three readings. The cost of *not* having that instrument is measurable: the first two rounds of this story were spent reasoning from the absence of an error line, which is exactly what a run that never reached the loader also produces. **An absence is only an observation when something was watching** — library lesson 02, met again from the other side.

Two consequences were named rather than absorbed, and both belong in the epic's ledger: ADR 01-08's profile seam loses its skills half (inert today, `full` being the only profile, and a real constraint on FR13's `lite`), and the clash alarm is gone with something worse in its place — two `skills` entries declaring the same name resolve last-one-wins with **nothing logged at all**. ADR 01-05's prefix is now the whole defence rather than half of one.

- Pattern worth reusing · Scope surprise · Testing gap — **`?? []` is how a test reads the wrong document and reports nothing.** The README's Permissions section had recommended OpenCode 2's `permissions` array — an array of `{ action, resource, effect }` — through four stories of a README the project had already retargeted at v1 alone. v1 does not ignore that key: it reports `Configuration is invalid` and the session does not start, so every reader who pasted the recommended block got a host that would not come up.

Ten tests in `permission-entries.test.js` were pointed at exactly this. They read the section's fenced JSON with `JSON.parse(block).permissions ?? []` and got an empty list, which every loop in the file passes over in silence — "every documented rule is well-formed" is trivially true of no rules, "every skill is covered by a recommended rule" was the one that should have failed and did not, because `allowed.length > 0` was the only floor and it was checked against a list built from the same absent key. `readme-v2.test.js` checked the same blocks for parsing to a non-empty object, which the wrong shape does. Four green files, a rule with a provenance comment, and a recommendation that could not load.

The floor idiom this project uses everywhere — assert the corpus is non-empty before filtering it — was present and did not help, because it was applied to the *result* of the wrong reading rather than to the reading itself. `rules.length >= 3` says the extractor found three things; it says nothing about whether the three are the three in the document. What catches this is asserting the **shape you refuse** as an absence, not the shape you accept as a presence: `refusedBlocks()` must be empty, driven red over a planted block first.

The general form: a reader with a default is a reader that cannot report failing to find its subject. Every `?? []`, `?? {}` and `?? ''` in a test that reads a document is a place where a renamed key becomes a clean pass.

**And the walk is what found it, which is the second half.** No amount of reading the README against itself would have surfaced this — the section is internally coherent and describes a real permission model, just a different host's. It took pasting the block into a project and starting `opencode`. Story 2 established that the suite could not see whether the host would accept dpm's modules; story 3 establishes the same about whether the host will accept dpm's documentation. Both were answered by one command, in a throwaway directory, in under a minute.

**Story 2 found a suite that could not see the host; story 3 found a suite that could not see the document.** The mechanism is the same and the tell is smaller: `JSON.parse(block).permissions ?? []`. A reader with a default cannot report failing to find its subject. Ten tests, each with an honest floor assertion, all reading a key that was not there and finding nothing to be wrong with.

The floor idiom this project uses everywhere was present and did not help, and understanding why is the transferable part. `rules.length >= 3` asserts that *the extractor found three things*. It does not assert that the three are the three in the document. The floor was placed one step too late — on the result of the reading rather than on the reading itself — and one step is all it takes.

**What catches this is asserting the shape you refuse, as an absence, driven red first.** `refusedBlocks()` must come back empty, and the control plants a block in the refused shape and shows the same reading finds it *and* yields no rules — the two facts that together made the old reading silent. That pairing is the reusable artefact from this story, and `tests/support/readme.js` is where it now lives so the two files that check the README's blocks cannot disagree about what they are reading.

Read against the epic as a whole, story 3 completes a progression. Story 1: a criterion described a mechanism that had moved. Story 2: an SDK described a route its own host could not reach. Story 3: a README described a host that was not the one it named. **Three artefacts, each internally coherent, each wrong about the running thing, and none of them detectable from inside the artefact.** The only instrument that found any of them was starting the host and looking — a `curl` against `opencode serve`, or one `opencode run` in a throwaway directory, in under a minute each. That is cheap enough that the honest conclusion is not "we should test more" but "the walk should have come first".

**Retired 2026-09-03T11:25:00.000Z**: Promoted to library 06. The `?? []` reading is the second of the three shapes that entry names, and the "assert the shape you refuse, driven red first" fix is now standing guidance rather than a lesson re-judged each run.
