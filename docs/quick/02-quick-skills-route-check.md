# The skills config route has no check that fails when it stops working

**Number**: 02  
**Status**: complete — All five criteria met, each driven red first. The skills config route is now exercised by running the host rather than by reading the tree. NFR3's substance is checked on every run; its coverage row is still unwritable, because a quick record carries quick_criterion rows and coverage binds to a story criterion.  

**Closed**: 2026-09-12T14:52:00.000Z  

## The change

DPM's skills reach an OpenCode v1 host through the host's own `skills` config key, pointed at this package's `skills/` directory. Nothing in the suite exercises that route. The nearest thing — `tests/v1-integration.test.js`'s skill count — reads `discoverSkills(packageRoot())`, which is dpm's own module over dpm's own directory, and would pass unchanged if the route broke completely.

**That was recorded rather than missed.** `registeredSkills()`'s docblock says it in as many words: *"It is a stand-in for the host and not the host"*, and *"The wider claim, that the arrangement loads at all, is not this function's to make and is not made here."* What was missing is the thing that does make it, which is what this record is for.

The check runs the host. `opencode debug skill` prints the whole resolved skill registry as JSON, so a throwaway directory holding one `opencode.json` is the entire fixture — no server, no session, and the probe returns in well under a second. Measured on OpenCode 1.18.30 on 2026-09-12: with the `skills` entry, 54 skills of which 23 are `dpm-*`; without it, 31 and none.

That is an oracle outside the pair, which is what the three library entries on this subject all point at. *Find the oracle before writing the expectation* — the host is a copy of the truth that dpm did not generate. *A check that shares its subject's error cannot fail* — its first shape is the driver that calls the export itself. *An absence is only an observation when something was watching* — a registry with no `dpm-*` entries is what a broken route and an unrun probe both produce, so the check asserts the probe exited and the registry came back populated before it reads any silence, and it asserts the tree's own set is non-empty, because two empty lists agree.

**Files affected**

- `tests/skills-route.test.js` — new. The probe, the set comparison against the tree, the containment reading, the control, and the ENVX1 stand-down.
- `tests/suite-integrity.test.js` — a third `CONDITIONAL_SKIPS` entry. That list is asserted as an exact set in both directions, so a new file that stands down has to be argued for there; the mechanism is being used as designed rather than worked around.

**One decision this sits beside.** ADR 02-03 accepted building on `skills.paths` "fenced and alarmed", and named the alarm as *"a registration-time check that turns the host silently discarding it into a loud failure"*. Epic 02-05 story 2 stopped dpm writing that key at all, so there is no registration to check at; the alarm moves to test time and the ADR's mechanism is overtaken while its intent is delivered. Worth a pivot on the ADR, not a silent divergence.

## What changed, and how it was verified

`tests/skills-route.test.js` runs the host. One case writes an `opencode.json` into a directory it owns, runs `opencode debug skill` there, and reads the registry the host resolved; a companion `[unit]` case drives the two readings that case depends on both ways without needing a host at all. `tests/suite-integrity.test.js` gained the file in `ADDED` and in `CONDITIONAL_SKIPS`, the latter being the list asserted as an exact set in both directions.

**Every assertion was driven red before it was accepted.** Pointing the `skills` entry at `shared/` gave an empty registry against twenty-three expected. Planting a `skills/dpm-malformed/` directory with no `SKILL.md` put a name in the tree's set that the host's did not carry — the other direction, and the realistic shape of "added but not picked up". Handing the control the `skills` entry made the control fail. A planted well-formed `dpm-phantom/` was picked up by the host immediately, which is the same reading passing for the right reason rather than by accident.

**The probe taught the check something on its first run.** Reading the host's stdout from a pipe came back truncated mid-string at about 64KB — the registry carries every skill's body and runs to several hundred kilobytes, and the host exits without draining. It surfaced as a `JSON.parse` throw, which is the loud failure the no-fallback rule exists to preserve: a `?? []` would have turned it into a clean pass reporting no dpm skills, which is exactly the reading a broken route produces. The probe now writes to a file.

Verified: 1184 passing and 0 failing with the host present; 1181 passing, 0 failing and 3 skipped with a `HOME` holding no `.opencode`, the third skip being this file standing down with its reason. `tsc --noEmit` clean and the module sweep clean.

**Two things this did not close.** NFR3's coverage row still cannot be written: `create_coverage` binds a requirement to a `story_criterion_id`, and a quick record carries `quick_criterion` rows, so the requirement reads as uncovered in the matrix while its substance is now checked on every run. And ADR 02-03's mechanism — "a registration-time check" — has nowhere left to live, because dpm stopped writing the key it would have guarded; the decision's intent is delivered at test time instead, and the ADR is the thing that is now out of date.
